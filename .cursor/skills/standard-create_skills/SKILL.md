
# 📜 如何新建一个 Skill

  - **概述**: 当**创建一个新的 SKILL 时**（`.md`）时，请按照下面的一些规范进行文档编写的约束，且注意保持简洁美观；长流程 Skill 须含进度台账约定。
  - **日期**: 2026-07-22

## 1 文件结构

  - 新建的 SKILL 放在当前项目中的 `.cursor/skills/` 目录下
  - 其命名范式为`standard-功能/SKILL.md`：
  - 示例如下

    ```markdown
    ├──.cursor/skills/
    │ ├── standard-xxx
    │ │   └── SKILL.md
    │ └── standard-xxx
    │     └── SKILL.md
    ```

## 2 内容规范

### 2.1 Header

  - SKILL 标题：emoji + 名称
  - 标题下方附文，说明本 Skill 的触发场景与创建时间。字段含义：
    - **概述**：一句话说明本 Skill 的适用场景（何时触发、做什么）。
    - **日期**：使用**当前日期**，格式 `YYYY-MM-DD`。

  - 示例如下：

    ```markdown
    # 📜 Skill 标题
    
      - **概述**: 简述本 skill 的功能与触发时机。
      - **日期**: 2026-07-16
    ```

### 2.2 正文结构

  - **标题格式**：
    - 一级标题：（`## 1`、`## 2`、...）。
    - 二级标题：（`### 2.1`、`### 2.2`、...）。
    - 三级标题：（`#### 2.1.1`、`#### 2.1.2`、...）
    - 四级标题：（`**(1)**`、`**(2)**`、`**(3)**`、...）
    - 五级标题：（`**a**`、`**b**`、`**c**`、...）
    - 六级标题：（`**(a)**`、`**(b)**`、`**(c)**`、...）

  - 每个小节应包含：**说明文字** + **示例代码块**（如适用）+ **注意事项**（如有）。

  - 示例结构如下：

    ```markdown
    ## 1 第一节标题

      - 说明文字……

        ```示例代码或伪代码```

      - **注意**：补充约束或边界条件。
    ```

  - **注意**：各节之间保持逻辑递进，避免内容重叠；示例代码务必能直接参考或运行。

### 2.3 书写风格

  - **语言**：默认使用中文，专有名词（函数名、字段名、命令等）保留英文原文。
  - **列表缩进**：正文列表项统一使用 **2 个空格**缩进，嵌套层再加 2 个空格。
  - **强调**：关键词、字段名、路径使用 `**粗体**` 或 `` `行内代码` `` 标注，避免过度强调。
  - **代码块**：必须标注语言（如 ` ```python `、` ```markdown `、` ```bash `）以启用语法高亮。
  - **简洁原则**：每条规范用一句话表达核心约束，避免冗余描述。

  - 示例（正确风格）：

    ```markdown

    - SKILL 标题：emoji + 名称

    - 标题下方附文，说明本 Skill 的触发场景与创建时间。字段含义：

      - **概述**：一句话说明本 Skill 的适用场景（何时触发、做什么）。
      - **日期**：使用**当前日期**，格式 `YYYY-MM-DD`。

    ```

## 3 工具索引规范

  当 Skill **需要调用外部工具/脚本**（如数据转换、环境检查、模型推理等）时，必须在正文中声明**工具索引**，让 Agent 在执行时能快速定位并正确使用。

### 3.1 何时需要工具索引

  - Skill 执行步骤中**调用了项目内其他脚本或工具**（不在本 Skill 内联实现）
  - 工具可能**不存在、版本不同或路径不固定**，需要 Agent 在运行时确认
  - 工具依赖**特定环境**（conda 环境、GPU、第三方库），需要前置检查

  - **不需要**：工具代码直接内联在 Skill 中，或工具仅为示例无实际执行

### 3.2 工具索引结构

  使用**表格**声明，至少包含以下三列：

  | 规范/分类 | 工具路径 | 用途 |

  - **规范/分类**：将工具按所属规范或功能分组（如 YOLO / Grounding / CD），便于快速筛选；若无需分组可省略此列，用 `通用` 代替。
  - **工具路径**：**相对路径**（相对于约定的工具根目录，如 `1-PROCESS/`）；若路径固定则写绝对路径并用反引号包裹。
  - **用途**：一句话说明脚本功能，格式为 `输入格式 → 输出格式` 或简要描述。

  示例：

  ```markdown
  ## 3 工具索引

  | 规范 | 工具路径（相对 `1-PROCESS/`） | 用途 |
  |------|----------|------|
  | YOLO | `utils/convert_json2txt.py` | Labelme JSON → labels/ |
  | YOLO | `utils/convert_xml2txt.py` | VOC XML → labels/ |
  | YOLO | `tools/yolo_dataset_division.py` | 生成 train.txt / val.txt |
  | CD | `utils/convert_json2mask.py` | json/ → label/ mask |
  | 通用 | `scripts/check_env.sh` | 验证 conda 环境可用性 |
  ```

### 3.3 工具依赖声明

  若某个工具**依赖特定环境或前置条件**，在工具索引下方补充说明：

  ```markdown
  - **注意**：`tools/xxx.py` **唯一依赖 `ultralytics`**；调用前须确认 `yoloe` conda 环境已激活。
  - **注意**：`utils/sam2_mask_gen.py` 需要 `sam2` 模型权重位于 `weights/sam2_hiera_large.pt`。
  ```

  - 依赖声明以 `**注意**` 开头，紧跟在工具索引表格之后。
  - 明确说明**依赖什么**（环境/库/权重/配置文件）以及**如何确认**（如 `conda run -n <env> python -c "import xxx"`）。

### 3.4 工具根目录约定

  若工具分布在**多个 Skill 共享的目录**，在工具索引开头声明根目录：

  ```markdown
  - 工具根目录：`/home/yulin/1-project/1-PROCESS/`（各 Skill 共用）
  ```

  - 若工具路径为绝对路径，在表格中省略「相对路径」说明，直接写 `` `绝对路径` ``。
  - **禁止**在多个 Skill 中重复定义相同的工具索引——优先引用已有索引，仅在新增工具时追加。

### 3.5 工具调用约定

  若工具需要**特定执行方式**（如必须用 conda 环境、必须传环境变量），在工具索引或依赖声明中一并写明调用模板：

  ```markdown
  调用方式：

  ```bash
  source "$(conda info --base)/etc/profile.d/conda.sh"
  conda activate <env_name>
  python <tool_path> --arg1 value1 --arg2 value2
  ```

  - 验证命令：`conda run -n <env_name> python -c "import required_pkg"`
  - 未安装时提示用户配置环境，**不得**用系统 Python 强行运行。
  ```

## 4 进度台账规范（todo.md）

  长流程 / 可断点续跑的 Skill，**必须**约定进度台账，对抗上下文截断；新会话以文件为准续跑，不依赖对话记忆。
  参考实现：`.cursor/skills/agent-automerge/SKILL.md` §1。

### 4.1 何时需要台账

  满足任一条件即须在 Skill 中声明台账：

  - 流程跨 **多个可恢复节点**（训练、推理、过滤、交付等）
  - 单步耗时长，或存在 **循环**（对 N 个子集 / M 个类别逐个处理）
  - 预期会 **跨会话**（用户说「继续」「接着跑」）
  - 产物路径多，续跑时需对照磁盘避免重做

  - **不需要**：单次问答、纯文档规范、一步内可完成的短脚本调用。

### 4.2 在新 Skill 中如何声明

  **(1)** 执行前检查中写明台账路径，并标注「⭐ 强制维护」。

  **(2)** 正文专设一节（建议靠前，如 `## 1 进度台账`），至少包含：路径、何时读写、模板、更新规则。

  **(3)** 工具索引表中增加一行：`进度台账 | <path>/todo.md | 断点续跑；强制读写`。

  **(4)** 各阶段结束处写清「本节完成后：更新 Checklist / phase / next」。

  - **注意**：台账文件放在该 Skill 的工作目录下（如 `<workdir>/todo.md`），**禁止**只写在对话里。

### 4.3 最小模板（可增行不可删节）

  状态枚举统一：`pending` / `in_progress` / `done` / `blocked` / `skipped`。

  头部字段（强制）：

  | 字段 | 含义 |
  |------|------|
  | `updated` | 最后写入时间 |
  | `phase` | 当前阶段枚举（按本 Skill 流程自定义） |
  | `current` | 正在做的事（一句话，始终非空） |
  | `next` | 下一步可直接执行的动作（始终非空） |
  | `blocked` | `无` 或阻塞原因 |

  正文区块（按需裁剪，长流程建议齐全）：

  - `## Meta`：输入路径、环境、关键配置
  - `## Checklist`：与 Skill 章节对齐的勾选列表
  - `## <循环表>`：循环单元一行（如 Train / Prelabel），含 `status` 与产物路径
  - `## Notes`：决策、例外、外置大表链接

  通用骨架示例：

  ```markdown
  # <SkillName> TODO

  - **updated**: YYYY-MM-DD HH:MM
  - **phase**: <stage_a> | <stage_b> | ...
  - **current**: ...
  - **next**: ...
  - **blocked**: 无

  ## Meta
  - ...

  ## Checklist
  - [ ] §2 ...
  - [ ] §3 ...

  ## Loop (按单元一行)
  | id | status | artifact | note |
  | --- | --- | --- | --- |
  | ... | pending | | |

  ## Notes
  - ...
  ```

### 4.4 读写与更新规则（写入 Skill 正文时可原文引用）

  **何时读写**：

  **(1)** **开跑 / 续跑前（强制）**：先 Read 台账；从未完成项继续，禁止无故重做已 `done`。

  **(2)** **每完成一个可恢复节点后（强制）**：立即更新（状态、路径、统计、`next`），再继续。

  **(3)** **长循环自检**：每完成 1 个循环单元，或长耗时步骤结束时，重读台账并核对磁盘产物。

  **(4)** **用户说「继续」「接着跑」「check 进度」**：先读台账，摘要后再执行 `next`。

  **(5)** **文件不存在**：按本 Skill 模板新建后再开跑。

  **更新约束**：

  - 只改本流程字段；保留历史 `done` 行以便跳过。
  - `status` 与磁盘一致：台账写 `done` 但产物缺失 → 改回 `pending` / `blocked` 并注明。
  - 大表可外置到 `tables/`，台账内只留路径链接。
  - **真相源**：对话摘要与文件冲突时，以 **台账文件 + 磁盘产物** 为准。
